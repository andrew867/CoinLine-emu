# ADSI physical interface and first-response timing handoff

## Current qualification

The graphical terminal has already received real analogue audio through a local voice-service connection, detected CAS, generated its own DTMF A acknowledgement, decoded Bell 202 CONNECT data without framing errors, and generated D1 acknowledgements. The outstanding milestone is a timely **first** completed D digit after CONNECT, followed by a complete menu dialogue. A successful retransmission is not equivalent to first-response acceptance.

This handoff describes observable hardware behavior, not firmware internals to reproduce in the emulator. Keep the original terminal executing its normal control flow.

## Board and signal contract

| Boundary | Required behavior |
| --- | --- |
| Later control-board clock | 24.576 MHz oscillator, 12.288 MHz effective CPU clock. Detector polls measured at 1.25 ms; executive timers advance in 10 ms ticks. The earlier 12.288 MHz oscillator profile must remain separate. |
| Analogue input | Continuous 8 kHz PCM, with independent CAS and Bell 202 detection. A nominal 85 ms CAS contains 680 samples. Silence must represent actual line silence, not a missing network packet. |
| CAS | Simultaneous 2,130 Hz and 2,750 Hz components; reject either component alone. Expansion status read `0x80`, mask `0x04`, is **active low** at the CPU interface. In the live bench the detector was asserted for 80 emulated ms after processing an independently verified 85 ms waveform. |
| Downlink | Bell 202, 1,200 baud, 1,200 Hz mark, 2,200 Hz space, serialized into the processor's asynchronous channel 1. Preserve actual framing, bit order, parity and stop-bit settings. |
| Carrier | The modem's serial detection register (register 2) uses mask `0x08`, set when carrier is present and clear when absent. The expansion status port also defines an active-low carrier bit (`0x80` read, mask `0x08`), but the later firmware qualifies carrier through the modem register. These are two distinct status interfaces, not the same polarity or necessarily the same physical signal. |
| Carrier qualification | The terminal detects an edge and then qualifies the same level on two subsequent polls. Do not add another long artificial debounce or independently deassert the status while unread character data remains queued. At the later-board poll rate, the two follow-up polls are 2.5 ms apart from the first observation in aggregate. |
| Uplink | DTMF generated by the terminal's modem and relay-control hardware, including A, D and the subsequent decimal message count. Do not replace it with a fabricated protocol acknowledgement. |
| Audio switching | Modem transmit/receive, handset mute, telephony isolation and connection to the office are distinct mechanisms. Preserve actual control-register transitions and their audio consequences. |

The physical UART bit stream must deliver the final stop bit before the exposed carrier falls. Decoder detection, serial queue drain and CPU-visible availability are different events. A byte decoded into a host queue is not yet a byte accepted by the processor. The current bench has already corrected one premature carrier-release path; preserve that correction. The graphical expansion has separate control/read decodes at `0x80` and `0x81`; preserve display controls independently of modem controls. An older design also defines a Bell 202/212 selection on a shared output mask, which is used for the alerter route in the later-board profile. Do not treat that mask alone as a universal receiver-mode selection. The later profile configures the modem control registers directly.

Physical service evidence confirms a separate removable ADSI daughterboard covering the firmware devices on the multi-application control board. See the firmware product bulletin, release 02 (February 7, 2000), pp. PB-7 to PB-8 Figs. PB-1/PB-2; and the multi-pay replacing-parts guide P0883897 (June 1998), pp. 4-9 and 4-13. The existing photo-derived motherboard modem identification does not establish the chipset on this daughterboard. A readable board photograph or schematic is still needed to establish the actual analogue detector, timing and connector pinout.

### Modem topology and component evidence

Earlier design descriptions explicitly distinguish the normal Bell 212A modem from a separate Mitel Bell 202 receive modem and describe both being connected during an ADSI session. The earlier selector is described as `0xC3`, mask `0x04`, set for Bell 202 and clear for Bell 212; this is consistent with multiplexing the demodulated serial stream to the shared CPU UART, but its electrical realization is unverified. The normal modem handles DTMF transmission; the ADSI service does not require a second full-duplex data connection. The later graphical revision changed the active hardware control sequence and uses the same output mask for the alerter. Do not infer the final receiver connection from the historical selector alone.

| Observable interface in the later profile | Function |
| --- | --- |
| CPU output `0x41` bits 0, 1, 2, 3 and 4-6 | Serial modem register data, clock, read/write strobes, and three register address bits respectively. This is the control/status interface, **not** the modem data UART. |
| CPU read `0x41`, bit 4 | Serial modem-register readback data. |
| CPU asynchronous channel 1 | Receive bitstream from the selected analogue demodulation path. |
| Expansion read `0x80`, bit 2 | Raw active-low CAS indication before native software qualification. |
| CPU write `0x40`, masks `0x02` and `0x04` | Native modem/telephony route and current-sink controls. The terminal mutes the handset before switching routes and later restores the prior route. |
| Serial modem register writes `0:20`, `3:00`, `4:04` (hex) | Select FSK modulation, enable receive output, and run the modem DSP in the later graphical design. |

The motherboard's photo-derived TDK 73K324L identification is consistent with the eight-register interface, including its active-high carrier bit and active-low DSP reset. Its published FSK modes are V.21 and V.23, not explicitly Bell 202. In particular, `0x20` selects the ordinary FSK/V.23 mode according to that part's data sheet; the successful emulated Bell 202 receiver does **not** prove that the photographed 73K324L alone performs Bell 202 demodulation in the actual graphical hardware. The earlier TDK 73K302L, also mentioned in historical modem support, does specify Bell 202. It is not confirmed as the final expansion-board component.

A plausible earlier daughterboard receiver is the period Mitel MT8843 or related CID/ADSI component, because it provides Bell 202/V.23 reception, a serial data output, carrier indication and a dual-tone detector. That is a component-family hypothesis, not a recovered part number. Its manufacturer application note distinguishes an early tone indication (typically 3-4 ms) from a separately qualified CAS indication with an example 66 ms guard interval. The native terminal itself requires roughly 64-65 ms of uninterrupted asserted samples to qualify CAS at 1.25 ms sampling. Cascading a second full 66 ms guard would therefore be inconsistent with recognizing the observed 85 ms CAS waveform. Model an early detector output and let the terminal perform its own qualification; don't assume a specific Mitel pin or exact filtering delay without a physical capture.

Manufacturer references: [TDK 73K324L data sheet](https://tvsat.com.pl/PDF/7/73K324L_tdk.pdf), [TDK 73K302L data sheet](https://files.tapr.org/product_docs/Pic-E/datasheets/73k302l.pdf), and [Mitel MT8843 preliminary data sheet](https://www.futurlec.com/Datasheet/Zarlink/MT8843AE.pdf), with [Mitel MSAN-164 application note](https://www.electronicsandbooks.com/edt/manual/Electronic%20Component%20Databook%20Datasheet/Brand/Mitel%20semiconductor/Application%20Note/MSAN164%20c19970520%20%5B83%5D.pdf). These are manufacturer-authored publications hosted by archives. They establish component capabilities and representative timing, not installed component identity or the terminal's specific circuit.

The independently verified CONNECT frame is `84 05 01 8E 00 86 00 62` (hex). Its eight octets sum to 512, or zero modulo 256. It is a useful deterministic fixture for the analogue waveform and UART acceptance test; delivery of decoded bytes alone is not a substitute for the analogue input.

## Why the first CONNECT differs from a retry

The first valid CONNECT enters ADSI from an ordinary voice session. It clears the stored softkey definitions, display information, input formats and related user-interface context. The switch into data mode also updates the softkey presentation before the data-mode transition is delivered. A repeat CONNECT arrives after some of that setup has already occurred. In the voice-side state, simultaneous mode-transition and qualified carrier-drop events select a 50-tick timer. In the data-side state, qualified carrier drop selects a 10-tick timer. Both are genuine terminal decisions; they are not detector settings.

Observed quiet and instrumented runs show the following:

| Measurement | First CONNECT | Repeat CONNECT |
| --- | ---: | ---: |
| Selected silence timer | 50 ticks (500 ms) | 10 ticks (100 ms) |
| Native carrier release to D onset, instrumented run | 846.391 ms | 456.303 ms |
| Interval remaining after nominal silence timer | 346.391 ms | 356.303 ms |

The measured inter-response difference is **390.088 ms**, close to the 400 ms difference between the selected timers. The residual is similar in both cases; it includes other terminal processing, switching and scheduling, and must not be treated as a measured relay settling time. In the instrumented first response, qualified carrier loss preceded the mode transition by 19 executive ticks (190 ms). The service-side completed-D interval was 1,006 ms, just 6 ms beyond its 1,000 ms deadline. A separate quiet run missed by 370 ms, and its transmitted FSK packet timestamp span was also irregular. This is not yet evidence that the remaining delay is entirely intrinsic to the terminal or entirely caused by the emulator.

## Recommended emulator investigation

1. **Decouple protocol timing from transport jitter.** Feed a recorded or independently generated CAS and valid CONNECT waveform through the actual native audio input at exactly its declared sample rate. Use a deterministic local sample schedule, not wall-clock sleeps inside the audio path. Start with a single valid CONNECT, no network retry. Compare with the production-style RTP route using the identical waveform.
2. **Instrument one common emulated-time timeline.** Record PCM sample indices, detector assertion/release, serial bit boundaries, final UART stop bit, receiver status changes, the number and timing of the carrier-status reads, DMA begin/end events, VFD ready and writes, telephony requests/responses, modem relay changes, and the actual first/last samples of D. Record wall-clock packet arrival/capture times separately. Do not subtract timestamps from the two clocks without a measured alignment.
3. **Measure the first-session initialization.** Specifically compare DMA activity for banked text, softkey and input-format clearing; display-page writes and ready polling; and the telephony keypad-disable exchange on initial CONNECT versus retry. These operations precede the mode transition and are plausible contributors to the measured 190 ms lead of carrier drop. They are not proven root causes. Check DMA completion timing against native CPU clock and that no artificially slow dispatcher or display-ready timeout is introduced per operation.
4. **Check receiver and scheduler boundaries.** The 1,200-baud character duration at 8N1 is approximately 8.333 ms. A receiver that decodes and then regenerates the complete character incurs a serialization delay; bound its queue depth and verify the final byte is not held behind transport polling. Verify the programmed UART baud on the later board, including divisor and peripheral-clock domains. Advance scheduled serial edges at their intended times even when host audio packets arrive in bursts.
5. **Measure the residual latency.** Partition the roughly 350 ms non-silence interval into carrier qualification, time to timer start, timer expiration to tone request, physical relay / mute changes, tone onset, and audio output buffering. Some of that interval may be required by the actual terminal. A correct model should expose each contribution instead of shortening the terminal's timer or skipping relay actions.
6. **Preserve bounded playout.** The existing two-frame cushion addresses observed RTP scheduling gaps. Confirm continuous sample count and correct ordering without extending the waveform, synthesizing zeros into active FSK/CAS, dropping samples, or delaying a completed tone behind another unrelated queue. Separately check real-time emulation speed and host scheduling under quiet and traced runs.

If the offline, cycle-faithful fixture still exceeds the deadline, record a terminal/profile versus service timing incompatibility, with the observed native timing and wire timing. Do not tune the hardware solely to force a protocol pass. A justified service interoperability policy, if eventually needed, is a separate decision from hardware emulation.

## Acceptance matrix

| Test | Expected result |
| --- | --- |
| Direct waveform, CAS | Correct A acknowledgement within the current service's 500 ms capability window, no response to a single-tone control input. |
| Direct waveform, first valid CONNECT | Correct decoded octets, no framing errors, first D and count generated by the terminal; record native timings. |
| Initial and repeated CONNECT, measured separately | Explain actual 50/10-tick selection and every material difference in the timing timeline. No duplicate or stale acknowledgement counted as a pass. |
| Full local voice route | Completed first D within the configured service's 1,000 ms window and correct subsequent count, followed by the server's actual menu. Repeat at varied sample and packet phase with the same deadlines. |
| UI round trip | Menu text and softkey labels appear from received data; physical softkey input produces the actual upstream DTMF action. |
| Voice, data, hangup | Correct modem selection, audio routing, data-to-voice return and disconnect, with no residual carrier/queue on the next call. Ordinary NCC sessions and ordinary voice calls remain qualified separately. |

## Protocol reference

[ETSI ES 201 071 V1.1.2 (1998), Annex A](https://www.etsi.org/deliver/etsi_ES/201000_201099/201071/01.01.02_60/es_201071v010102p.pdf) establishes the FSK-downlink / DTMF-uplink service model. It is a European adaptation, not proof that every local timing requirement matches this North American terminal. The bench measurements and current service deadline above are independent acceptance evidence.
